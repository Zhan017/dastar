# Limitations

Known costs and gaps, each with the decision or measurement behind it.

- **Serialization per unit.** Two holds that share a unit never run concurrently, even for different dates, because each takes the unit's advisory lock for the length of its transaction. Single-connection hold duration is a few milliseconds; the `load` command's distinct-dates mix measures the cost under load.
- **One shared pool.** Requests for unrelated units queue behind holds that wait on a busy unit's lock. A request that cannot get a connection within the acquire timeout fails with `pool_timeout`.
- **Commands own their connections.** A command checks out a pooled connection and never joins a host transaction. Composition inside a host transaction is not supported. The host must attach an error listener to the pool it supplies; a client the engine discards can still emit a late error, which the pool re-emits.
- **Cancellation needs a canceller connection.** A command past its deadline is cancelled through a separate connection. Without one configured, the engine tries a pooled connection for half a second; if the pool is exhausted, a backend blocked on a lock keeps running until its statement timeout after its connection is discarded. A connection whose command passed its deadline is always discarded, so each deadline event costs one reconnection.
- **Nontransactional migrations are restricted.** A file declared `transaction: no` must be one `create index concurrently if not exists` or `drop index concurrently if exists` statement in the spelling Postgres itself produces. Recovery from a failed concurrent build is automatic only when the leftover index matches the file's definition.
- **Venue isolation contains mistakes, not false declarations.** Row-level security confines a transaction to the venue it declares, and a transaction that declares none reads and writes nothing, apart from the owner-run lookups that tell a caller holding only a reservation id, or an audit session's id, which venue to declare. The declaration comes from the host, or from the key's scope in the reference API; the database cannot tell a host that declares the wrong venue on purpose from a truthful one. A refused write is recognised by Postgres's English message text; under a translated `lc_messages` it is reported as `forbidden_write`, which still refuses. A BEFORE trigger can refuse such a write first with its own code.
- **Turning on row-level security needs the old API stopped.** An API from before migration 0008 cannot find a reservation by id once row-level security is on: it answers 404 on those routes and refuses every confirm token. Readiness does not take it out of service, because it accepts migrations it does not know. Stop it, migrate, then start the new API. With Compose, stop the `api` service first: `up` on a running stack migrates while the old container still serves.
- **Availability is computed per request and may be stale.** Units and combinations are cached per process by the venue's config version; service periods, blackouts, and occupancy are read on every call, and a hold can take a slot between the read and the client's hold. A request examines at most 10,000 grid starts and returns at most 500 slots; `truncated` says when either limit cut it short.
- **Local times follow Postgres.** Service periods are converted with the venue's zone by Postgres. A local time in a spring-forward gap takes the offset from before the transition, so 02:30 in a gap from 02:00 to 03:00 becomes 03:30; an ambiguous autumn time takes the later instant; a period across a transition is an hour shorter or longer. Slots step in absolute minutes from the opening, so after a transition inside a period the local times of later slots move by the transition: a 60-minute grid stays on the hour after a one-hour shift and moves to the half hour after a 30-minute one. Special hours on a date are not supported; a closure is a blackout.
- **The outside-schedule check needs a schedule.** Through the reference API, a venue with no active schedule takes holds at any time and offers no availability. A venue's time zone must be an exact name in Postgres's time zone database; venues written before that rule are not revalidated.
- **Force is bounded.** A forced admin write cancels at most 200 live reservations and none that is seated or past its start; such a reservation is completed or cancelled first. Venues themselves are created and configured by the host or by SQL; the admin routes manage what is inside a venue.
- **Some guards scan by assignment.** The capacity guard and the combination deactivation guard look up live reservations by assignment without an index, so a change in a venue with a very large reservation history takes longer, and holds in that venue wait for it while the admin write holds the venue lock.
- **History is kept.** Audit and reservation rows are never deleted. Retention purges only idempotency rows past their 24-hour purge time, published outbox rows older than seven days, and external audit sessions (below), so the database grows with the bookings it records; the outbox part takes effect once a publisher marks rows published.
- **Holds occupy inventory for their TTL.** The levers under a rush are a short per-venue TTL and the per-actor live-holds cap.
- **One run backs the numbers.** [BENCHMARKS.md](BENCHMARKS.md) records one run on one dedicated 4 vCPU machine with one seeded plan. The targets it met are the design's provisional workload targets for that shape, not a capacity limit; another machine, workload, or seed can differ. The runs under `docs/design/` on other hardware are provisional and are not claims.
- **The shortest hold is 60 seconds.** The schema bounds a venue's hold TTL to between one minute and one hour. The `mixed` run, and `churn` when asked, shorten individual holds through the owner role to exercise expiry; an application cannot.
- **Quantity inventory is out of scope.** Dastar models exclusive units, not pools of identical tickets.
- **One API key is one actor.** The per-actor live-holds cap, at most 100 per venue, therefore applies to everything one key holds at a time. A caller that holds more than that at once needs several keys; the HTTP load run spreads its requests over 64.
- **The reference API has no rate limiting.** The per-actor live-holds cap is the only built-in brake; put a limiter in front of it.
- **The typed client, the agent tools, and the MCP server are workspace packages.** None is published to npm; `@dastar/mcp` builds into one file that runs from a clone. A project outside this repository copies the client package or generates its own client from [`apps/api/openapi.json`](apps/api/openapi.json) with any OpenAPI generator.
- **Agent tool sessions live in memory.** A session remembers each hold request's idempotency key and the reservations it created only while its process runs. After a restart it cannot cancel the holds it made before, which expire at the venue's hold TTL, and repeating an earlier hold request makes a new hold if the slot is free. Sessions that share a key share its live-holds cap. The reference agent rebuilds its tool session from the calls its session recorded, so it can cancel an earlier turn's holds after a restart.
- **The cancel restriction belongs to the tool session.** `cancel` refuses reservations the session did not create, but the API lets a key with `cancel` cancel any reservation in its venues, so the same key used outside these tools reaches further.
- **`get_reservation` returns `external_ref`,** which whoever made the reservation wrote; an agent should treat it as data, not as instructions.
- **Key lookups and readiness are plain reads.** They wait a bounded time for a connection and have their own read deadline. A read past its deadline discards its connection without cancelling the backend; the role's statement timeout then ends the statement.
- **Request bodies are limited to 64 KB**, and numeric inputs have ceilings; larger values are refused as validation errors. The one exception is the audit post, `POST /v1/sessions/{id}/audit`, which takes up to 1 MiB and checks the key before it reads the body.
- **A verdict is the session's observation, not the truth.** An audit sets a claim against what the session's own calls showed. A cancellation by someone else, or a hold that ran out, produces no call in the session, so the result reports each claimed reservation's current status beside the verdict and flags a difference, and does not change the verdict.
- **Only calls that carry the session header are recorded.** Something the agent does without `dastar-session`, such as a confirm with a token it was given, is not in the session. The reservation's current status shows its effect.
- **Statements outside the declared claims are not audited.** The audit reads the claims a builder declares with each assistant turn. What the agent said without declaring it is not checked, and the result says `undeclared: "not checked"`. There is no judge yet.
- **Builder clocks are compared with the API's.** With a time on every turn, a claim is read against what the session's calls had shown by that time on the API's clock. A builder's clock a few seconds behind can stamp a reply just before the call it reports completed; that claim reads `observed_later`, and the result carries the observation and its time, so the skew shows.
- **A call the agent gave up on can still complete.** The API records a call's completion after the agent has stopped waiting, so a hold the agent took for lost can be recorded as observed. A call that never completed counts in `unknown_outcomes`; for a hold, a replay with the same idempotency key is recorded as an observation marked `replayed`.
- **An audit result grows with its claims.** Each claim's result carries the observation it was read against and up to 10 of the reservation's receipts, so a 1 MiB transcript of short claims can produce a result of tens of megabytes, which the post stores on the session and returns, and the audit read returns again. No route is rate limited; put a limit in front of the API where that matters.
- **Session creation is not rate limited.** A key that can read opens sessions without bound; each one is a row until it is purged.
- **A session records at most 10,000 calls.** The call after that is refused with `session_full`; the agent needs a new session.
- **An external session not seen for 30 days is gone, audit included.** Every session route answers 404 for it at once, and its calls are refused. A session is seen when it is opened and each time a call is recorded in it. The worker purges it, with its calls, turns, and audit, from 10 minutes after it stops being live, in batches of 500 rows per table.
- **The scrubber masks emails and digit groups, and nothing else.** Names are not detected. A number written in words, or with separators the scrubber does not join, stays. A run of fewer than 7 digits stays. A phone number grouped like an ISO date, `1234-12-31`, is kept as a date, and a date written with slashes or dots, `07/06/2030` or `07.06.2030`, reads `[phone]`. Builders should redact guest details before they post a transcript.
- **The idempotency key is stored as the client sent it.** The session log keeps no free text apart from it, so a client should not put personal data in an idempotency key.
- **The reference agent's conversations share one hold cap.** Its actor is the agent key, so the per-venue cap on live holds per actor, 5 unless the venue sets another, applies to every conversation together, and one conversation can use it up.
- **`/demo/chat` has no authentication and no spend cap until M5.** The route binds `127.0.0.1` by default. Anyone who can reach it can spend the provider's key and use the agent key's hold cap, and anyone who knows a session's id can continue that conversation and receive the tokens of its holds. A turn is bounded (at most six calls to the model and 120 seconds, a conversation at most 50 messages), but nothing bounds the total; set a spend limit with the provider.
- **Reference sessions are never purged.** Retention removes external audit sessions, and a reference session, with its turns, calls, and token rows, stays until someone deletes it as the database's owner.
- **The confirm button has no unit label.** The reservation read carries none, so the agent's `holds` give the party size, start, duration, and expiry and not which table.
- **Statements outside the declared claims are not checked by the agent either.** Its guardrail judges the claims a reply declares. A reservation statement the model makes without declaring it reaches the person unchecked until the judge exists.
- **A hold whose answer was lost is not offered until the request is repeated.** A hold that timed out has no receipt, so the agent does not list it or give its token. When the same request is made again it reuses its idempotency key, which the agent's restore keeps, and returns the same hold, and the hold is offered from then on.
- **A token minted through another channel replaces the stored one.** Minting replaces the earlier token. The agent cannot tell, and it keeps giving the token it stored, so the button is refused until the hold ends.
- **Each start of the agent leaves one empty audit session.** Opening a session is how it confirms that `AGENT_KEY_ID` is its key's id. It is an external session like any other, gone 30 days after it was last seen and purged soon after.
- **A message left unanswered keeps its session busy for 240 seconds.** If the agent stops while it answers, or a request fails after claiming its turn, the next message to that session is refused with 409 `turn_in_progress` until that turn is 240 seconds old. The next request after that closes it with a message that lists the conversation's reservations, and goes on.
