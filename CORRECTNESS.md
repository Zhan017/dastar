# Correctness

What the database enforces, how, and which test would show it broken. Guarantees are properties the schema is designed to enforce and the tests confirm or falsify. Hypotheses are runtime properties that only measurement settles.

## Venue isolation

Invariant 10 sits behind boundary B ([SECURITY.md](SECURITY.md)): the caller declares the venue, and the database confines the transaction to it without being able to tell a true declaration from a false one. Invariants 1, 2, 4, 5, 7, 8, 9, 11, and 12 sit behind boundary A and do not depend on that declaration. The triggers that read other rows to enforce them (the fit check, the capacity guard, the unit-row insert guard, the membership check, the two blackout guards, and the two deactivation guards) run with the owner's rights, so row-level security, which follows a setting the caller controls, never changes what they see; `venue-isolation.test.ts` clears the setting before commit and still gets `assignment_mismatch`. The hold's overlap query reads `dastar.occupancy`, an owner view with the policies' own filter, because row-level security would otherwise keep the range index out of the plan; the same test pins the index condition.

## Effective status

Reads return `expired` for a stored `held` row whose expiry has passed by database time, whether or not the sweeper has reached it. The stored column catches up when the sweeper or a hold's overlap pass expires the row.

## Availability

Availability is advisory. It reads service periods, blackouts, and occupancy in one repeatable-read transaction and offers starts a hold would accept at that moment: the schedule's duration for the party, an assignment that fits it, no active blackout over the booking, and no occupied unit over the booking padded by the schedule's gap. A concurrent hold can take an offered slot first, and the exclusion constraint decides. A hold of an offered slot can also be refused with the retryable `overlap_set_too_large` while the sweeper is far behind, because availability treats unswept expired holds as free and the hold counts them before it expires them. `availability-property.test.ts` holds a sample of the offered slots of random venues, one at a time, expecting each to be granted, and compares the offered starts with a model written independently in the test. Refusing a hold outside the venue's service periods is a policy of the reference API (`outside_schedule`), not an invariant.

## Admin writes

A change of configuration that would strand live reservations, judged by database time, is refused or forced. The capacity guard (invariant 4), the deactivation guards (invariant 12), and the blackout guard (invariant 11) refuse it in the database whoever writes it. The admin commands read the same set first, earliest start first: without force they refuse with its ids and write nothing; with force they cancel those reservations, each with a reason and a `reservation.cancelled` event, and apply the change in the same transaction, so the guards then pass. Force cancels only reservations that are not seated and whose start has not passed (`reservation_in_progress` otherwise) and at most 200 of them (`force_too_large` otherwise); a schedule change strands nothing, since outside-schedule bookings are a policy of the reference API.

## Model-based test

`model.test.ts` runs random sequences of commands against a reference model kept in the test, in `packages/db/test/model/`. Each run gets its own venue with a random floor plan, service periods, hold TTL, and live-holds cap. The commands are holds (with fresh, replayed, and reused idempotency keys, the schedule policy, and missing or inactive assignments), confirmation by key and by token, token minting, cancel, seat, complete, the sweeper, clock steps, reads, and admin changes to unit capacity and activity, combination activity, and blackouts, with and without force. After every command the test checks that the outcome is the model's; that every reservation's stored and effective status, version, expiry, and unit rows are the model's; that each reservation's audit rows and outbox events are the model's trail, so every transition writes exactly one of each and nothing else writes an outbox row (invariant 6 and outbox completeness); and, with queries of its own, invariants 1, 4, 8, 9, 11, and 12. It exercises the commands, not raw SQL: where a command refuses before a trigger would, as with its status checks and the admin commands' read of the stranded set, the trigger is out of reach, so the attack and guard tests remain what shows each trigger refusing on its own. Commands run one at a time, so the test sees no concurrency, and a confirmation never meets the blackout, activity, or capacity check that only a concurrent write can bring to it; the two-connection tests cover both. With the default seed and run count each outcome on a fixed list must come up, so a run that exercised too little fails. A failure prints the seed, the path, and the shrunk command list; `DASTAR_MODEL_SEED=<seed> DASTAR_MODEL_PATH=<path> pnpm --filter @dastar/db exec vitest run test/model.test.ts` replays it, and `DASTAR_MODEL_RUNS` sets how many sequences run.

## Confirmation near expiry

Postgres evaluates `now()` at transaction start. A confirmation that begins before a hold's expiry and then waits on a lock is judged by its start time, so it succeeds even if the wall clock passed the expiry during the wait. The wait can include the unit lock as well as the row lock. This is a bounded grace, not a defect. A capacity edit cannot exploit it: an edit and a confirmation on the same unit serialize on the unit lock, and whichever runs second sees the other's committed state, so the edit is refused or the confirmation is refused (`capacity-expiry.test.ts`). A blackout write judges a hold by its own clock, so it can admit a blackout over a hold that a confirmation begun before the expiry still sees as held. The confirmation therefore takes the venue lock shared and checks the blackouts under it, and whichever of the two runs second sees the other: the confirmation is refused (`blackout`), or the blackout write sees a confirmed reservation (`blackout_conflict`) (`schedules-blackouts.test.ts`). A deactivation also judges a hold by its own clock, so the fit trigger checks activity on the confirmation as well as on the insert: a confirmation that waited behind a deactivation which judged the hold expired is refused (`assignment_inactive`) (`admin-guards.test.ts`).

## Lock order

| Writer | Locks, in order |
|---|---|
| hold | venue advisory lock (shared) → unit advisory locks (sorted) → overlapping reservation rows (`order by id for update`) → own inserts |
| confirm | venue advisory lock (shared) → unit advisory locks (sorted) → own reservation row |
| capacity edit | the unit row itself (held by the UPDATE) → unit advisory lock → reads of reservations, no reservation row locks → the venue row (config version) |
| cancel, seat, complete, token mint | own reservation row only |
| batch expiry | reservation rows in batch, `skip locked`, no unit locks |
| blackout write | on an update, the blackout row itself (held by the UPDATE) → venue advisory lock (exclusive) → reads of unit rows and reservations, no locks on them → the venue row (config version) |
| unit or combination deactivation | the row itself (held by the UPDATE) → unit advisory locks (sorted) → reads of reservations, no row locks → the venue row (config version) |
| admin write (engine command) | venue advisory lock (exclusive) → stranded reservation rows (`order by id for update`, with force only) → its own row → the unit advisory locks its triggers take → the venue row (config version) |

Every command acquires resources in this order and never returns to an earlier stage, which is why the reference paths are designed not to deadlock. This is a hypothesis with named tests (`interleavings.test.ts`, `capacity-expiry.test.ts`, and for the venue lock `schedules-blackouts.test.ts`), not a proof (and for deactivations and admin writes `admin-guards.test.ts`, `admin-units.test.ts`, and `admin-calendar.test.ts`); a mixed-load run is not yet part of the suite. Writes outside the commands can take another order: a raw blackout update takes its row before the venue lock its guard takes, so it can deadlock with an admin write of the same blackout, and Postgres aborts one of them. Deadlock and serialization errors stay mapped to `serialization_conflict`, and the hold command retries once (`hold-retry.test.ts`). The assignment columns are immutable for the application role, which is what lets confirm look up the units to lock before it locks the row.

A hold's foreign-key checks take only a key-share lock on the venue row, which the config-version update does not conflict with, so a blackout write waits on no lock a hold holds once it has the venue lock. A transaction that writes more than one blackout, or a unit, combo, or schedule before a blackout, must take the venue lock exclusively before its first write; otherwise it can wait on the venue lock while holding a row that a holder of that lock waits on, directly or through another writer. Every admin command takes the venue lock exclusively before its first write. Under it no reservation of the venue is inserted or confirmed, since the blackout guard takes the lock shared on both, so the reservations a change would strand cannot grow while it decides.
